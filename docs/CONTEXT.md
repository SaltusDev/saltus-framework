# Context: Architecture & Decisions

## Architecture
The framework is built to be included within a WordPress plugin. It uses models (PHP/JSON/YAML) to define Custom Post Types and Taxonomies.
It searches for model files by default in the `src/models` directory.

### Initialization
```php
if ( class_exists( \Saltus\WP\Framework\Core::class ) ) {
    $framework = new \Saltus\WP\Framework\Core( dirname( __FILE__ ) );
    $framework->register();
}
```

## Key Decisions

### 1. Codestar Framework Integration
- **Purpose:** Used for rapidly building complex settings pages, metaboxes, and options panels.
- **Decision:** Instead of building a custom options framework from scratch, Codestar provides a robust, heavily tested foundation under a GPL license.
- **Trade-offs:** We maintain custom patches (`lib/codestar-framework/patches`) to tailor its behavior to our specific framework needs. This means updates to Codestar require manually re-applying patches via a script.

### 2. SoberWP/Models (Simplified)
- **Purpose:** Provides a declarative approach to registering Custom Post Types (CPTs) and Taxonomies.
- **Decision:** A simplified version of SoberWP/Models was included directly in the framework. This abstracts the repetitive and verbose WordPress core functions (`register_post_type`, `register_taxonomy`) into clean, easily readable PHP arrays, JSON, or YAML configuration files (models). 
- **Impact:** Speeds up development time for developers of any skill level by relying on simple configuration rather than complex procedural code.

### 3. Composer Classmap Autoloading
- **Purpose:** Handling legacy or third-party library loading.
- **Decision:** The project migrated from requiring 'files' directly to using Composer's `classmap` for libraries like the Codestar Framework.
- **Impact:** Enhances performance and standardizes autoloading. However, it introduces a manual step: developers must run `composer dump-autoload` whenever new classes are added to these mapped directories.

### 4. GitHub Updater Support
- **Purpose:** Plugin update management.
- **Decision:** Includes native support for `afragen/github-updater`.
- **Impact:** Allows plugins built with this framework to receive seamless updates directly from the WordPress admin dashboard, bypassing the need to host plugins on the official WordPress.org repository.

### 5. WordPress-Native MCP/Abilities
- **Purpose:** Expose Saltus model, content, settings, and metadata operations to AI clients through WordPress-native MCP/Abilities.
- **Decision:** WordPress 7.0 Abilities is the supported MCP path. The local stdio MCP server was removed; SSE transport and standalone server distribution remain out of scope.
- **Service Registration (Two-Pass Model):** To ensure REST endpoints and MCP tools are always available (regardless of whether the request is admin, frontend, or REST), `Core` registers `RestRouteProvider` and `ToolContributor` unconditionally on plugin boot. However, the core service activation (admin screens, scripts, hooks) remains strictly gated behind the `is_needed()` method. This prevents admin-only/frontend-only hooks and assets from running amok in contexts where they aren't needed.
- **Documentation:** the `docs/mcp/` section is the canonical source for the MCP surface — `index.md` (setup and discovery), `permissions.md` (capability and config gating), `runtime.md` (execution, caching, audit, health), and the generated `abilities.md`.
- **Metadata:** `list_meta_fields` exposes all registered CPT meta configs through `GET /saltus-framework/v1/meta`; `get_meta_fields` exposes one CPT through `GET /saltus-framework/v1/meta/{post_type}`.
- **Health:** `get_health` exposes `GET /saltus-framework/v1/health` through `saltus/get-health`, including version, error rate, latency, cache, rate-limit status, and rollup freshness.
- **Current Shape:** Metadata responses preserve the raw Saltus/Codestar config in `meta` and add `normalized.fields` plus `normalized.rest_meta_keys` for client write guidance.
- **Normalized Metadata:** Nested Codestar fields are flattened into paths such as `points_info.coordinates.latitude`, with label, source meta key, serialized status, REST writability, and JSON-schema-like type data.

### 6. Legacy Refactoring Track
- **Purpose:** Stabilize high-traffic legacy framework paths such as `Modeler.php`, `src/Features/`, and `Saltus*.php`.
- **Decision:** Refactoring these paths is debt reduction around runtime-critical behavior, not cosmetic cleanup. The goal is to reduce regression risk, improve standards compliance, and prepare the code for focused unit and integration tests.
- **Compatibility:** Existing Saltus plugins should continue working while internals become safer to maintain, easier to type-check, and easier to test.

### 7. Model-Driven Blocks
- **Purpose:** Provide editor-native list and single views without duplicating post data into block content.
- **Decision:** Blocks use runtime Block API v3 metadata arrays and one shared unbundled editor script. Model metadata supplies selectable field paths; dynamic PHP rendering reads current post values.
- **Templates:** Resolution order is consuming-plugin config, active theme override, then framework defaults under `templates/blocks/`.

### 8. WP-CLI Parity
- **Purpose:** Make the WordPress-native ability surface available to operators and scripts without HTTP dispatch.
- **Decision:** Eight `wp saltus` command groups call WordPress APIs and shared framework services directly. `CommandCatalog` is the authoritative 20-command parity map and generates `docs/guides/wp-cli.md`.
- **Outside the parity map:** two groups deliberately do not appear in `CommandCatalog`, so neither is published in the generated `docs/guides/wp-cli.md`. The `saltus config` group (v1.8.5) validates model config files rather than wrapping an MCP ability — it needs no WordPress boot and cannot drift from the ability surface. The `saltus metrics` group (v2.1.1) reads the audit rollup store rather than dispatching an ability, so there is no ability for it to stay in parity with.

### 9. Model-Scoped AI Governance Context
- **Purpose:** Expose normalized, per-model AI governance context (brand voice, audiences, field rules, allowed statuses, forbidden actions, human-review flag) to AI clients via REST and MCP.
- **Decision:** `AiContextProvider` normalizes raw model `ai_context` config against registered defaults (overridable via `saltus/framework/ai_context/defaults`). Mutating MCP tools are validated through `validate_mutation()` before REST dispatch, rejecting forbidden actions and disallowed statuses.
- **Surface:** `GetContext` MCP tool (`saltus/get-context`) + `GET /saltus-framework/v1/context/{post_type}` and the `wp saltus context get <post-type>` WP-CLI command.

### 10. Model-Driven Frontend Shortcodes
- **Purpose:** Render model-driven list and single views without writing template code, using a shared `FrontendRenderer` and configurable templates.
- **Decision:** `SaltusFrontend` registers the `[saltus_cpt]` shortcode (plus optional aliases) per model. Arguments are strictly validated/sanitized (limit clamp, allowlisted orderby/order, sanitized taxonomy and terms, path-traversal-guarded template resolution). Default templates ship under `templates/`.

### 11. Inside-Admin AI Assistants
- **Purpose:** Provide contextual AI suggestions and brand-rule validation inside configured post editors.
- **Decision:** `AiAssistantProvider` exposes fixed, model-scoped actions through `saltus/framework/ai/assistant_actions`. `AiAssistantProvider` first lets a consuming plugin handle an action via that filter; if none does, it generates content through the WordPress AI Client (`AiClient` + `ActionPrompts`) using credentials configured under Settings > Connectors. Saltus never reads, stores, or transmits API keys and hardcodes no provider or model. The `saltus/framework/ai/prompt_builder` filter lets consumers pin a provider or model.
- **Model Context:** `brand_voice`, `audiences`, and `field_rules` are composed into the AI client's system instruction, so prompts are model-scoped. Missing title/content/excerpt are filled from the post being edited.
- **Availability:** `GET /saltus-framework/v1/health` reports `ai.client_available` and `ai.connectors_available`; `wp saltus health` reports AI availability.
- **Scope:** Post editor screens only. Existing posts use `edit_post`; new posts use `edit_posts`. Suggestions require explicit editor confirmation before changing fields. On WordPress versions without the AI client, only the filter path applies.

### 12. Reflection-Based Dependency Injection
- **Purpose:** Let framework consumers register services with ordinary typed and positional constructors.
- **Decision:** `ReflectionInstantiator` is the default instantiator for both `ServiceContainer` and `GenericContainer`. It resolves named dependencies first, then positional values, compatible typed objects, defaults, and nullable parameters.
- **Compatibility:** Services that accept one `array $dependencies` parameter continue to receive the full dependency bag. Unresolvable required parameters fail with `FailedToMakeInstance::UNRESOLVED_ARGUMENT`.

### 13. AI Editorial Review Queue
- **Purpose:** Queue mutating AI/MCP changes for human approval before they are applied, enforcing the `human-review` governance flag end-to-end.
- **Decision:** `AbilityRuntime` gates every mutating tool behind `has_permission()` before governance, rate-limit, or dispatch work. When `ProposalService::should_queue()` matches a mutating tool, the runtime stores the change as a `pending` proposal via `ProposalStore` instead of dispatching it. A reviewer then approves or rejects the proposal through the REST review API or the "AI Review Queue" admin page; `approve()` applies the stored mutation and records the resulting post id.
- **Surface:** `EditorialReview` service, `EditorialReviewController` routes (`/proposals`, `/proposals/{id}`, `/proposals/{id}/approve`, `/proposals/{id}/reject`), and the `saltus-ai-review` admin management page.

### 14. WebMCP Browser Surface (Phase 8)
- **Purpose:** Project the existing Saltus tool registry into the browser as WebMCP tools, so an in-browser AI agent can call typed functions instead of scraping model-rendered markup.
- **Decision:** WebMCP is a third consumer of tool definitions alongside WordPress-native MCP/Abilities and WP-CLI. Two independent surfaces: `frontend: true` registers read-only tools on public views for anonymous visitors, `admin: true` registers capability-gated tools on wp-admin screens. `ManifestBuilder` projects Saltus tool definitions into WebMCP descriptors (JSON Schema input and character budgets); `PublicFieldFilter` narrows frontend output to public/model-declared fields, denying secret-like field paths outright. The browser is an untrusted client: every invocation is re-validated through `src/MCP/Validation` and rate limited, and only `publish`-status posts of publicly queryable models surface on the frontend. Public queryability is deliberately *not* required for the admin surface — an agent there acts as a user who can already reach the screen, so gating is by capability instead.
- **Untrusted-client budgets:** two guards exist because the endpoint is reachable by unauthenticated visitors. `ClientIdentity` keys the rate-limit window per caller (user id when logged in, otherwise a salted `REMOTE_ADDR` hash) so one agent cannot exhaust the window for the whole site; caller-supplied forwarding headers are ignored by design, since honoring them would let an agent reset its own limit. `ResultBudget` clamps a serialized result to 1500 characters, because agents enforce their own output limits by cutting mid-token — trimming server-side keeps the JSON well-formed and flags `truncated` so the agent re-queries instead of trusting a partial answer.
- **Governed writes (8B):** no WebMCP write tool mutates directly. `AdminTool` decorates an existing ability — name, description, parameters, and capability checks all come from the ability already registered for MCP/Abilities and `wp saltus`, so the browser surface cannot drift from the other two consumers — and routes every mutating call through `ProposalService` to the Phase 6B review queue, returning the proposal id and a review URL. This exists because WebMCP has no settled confirmation model (`requestUserInteraction()` is unresolved in the spec draft) and no authentication story at all; rather than invent one, writes go down the path Saltus already built. With the queue unavailable a write returns 503 rather than falling back to a direct mutation, so a missing dependency cannot silently become an unreviewed change. Write tools are not annotated `readOnlyHint` — a queued write still changes state, and that hint is the only signal that makes an agent confirm.
- **Discovery vs invocation:** `WebMcpTool::get_discovery_capability()` is separate from `has_permission()` on purpose. The latter answers "may this call proceed with these arguments" and usually needs a target id the manifest cannot supply, so listing a tool would otherwise depend on inventing arguments for it. A tool the current user could never call is never advertised.
- **Per-screen scoping:** `AdminScreen` + `AdminToolSet` map post editor / post list / settings / review queue to distinct tool sets. The discovery notes record Shopify shipping uniform tools across page types and some breaking where they did not apply; an agent cannot distinguish a tool that is wrong for the screen from one that is right. The review queue gets reads only — an agent proposing changes from the screen where a human reviews proposals would be arguing with itself.
- **Nonce lifecycle:** admin calls carry `X-WP-Nonce`; `/webmcp/nonce` issues replacements. The bridge retries a stale nonce exactly once, keyed on the server's `refresh` flag rather than the 403 status, because a genuine capability failure arrives as 403 too and retrying it just burns a request. The frontend payload carries no nonce — one bound to a session an anonymous visitor does not have would imply an authentication story the public surface lacks.
- **Surface:** `WebMcp` feature service, `WebMcpPolicy`, `AdminScreen`, `AdminToolSet`, `WebMcpTool` contract, `AdminTool`, `WebMcpController` routes (`/webmcp/manifest`, `/webmcp/execute`, `/webmcp/nonce`), `bridge.js` namespace-probing loader with nonce refresh and `saltus-webmcp-toolchange` re-registration, `wp saltus webmcp manifest|validate`, the `webmcp` block in health output, filters `saltus/framework/webmcp/tools`, `saltus/framework/webmcp/admin_tools`, `saltus/framework/webmcp/manifest`, `saltus/framework/webmcp/public_fields`, `saltus/framework/webmcp/client_identifier`, `saltus/framework/webmcp/output_budget`, and the guide `docs/guides/webmcp.md` (tool table generated by `composer docs:webmcp`). Research and the declarative-forms evaluation are recorded in the internal discovery notes.
- **Testing:** `bridge.js` is covered by `tests/js/bridge.test.js` on Node's built-in runner (`npm test`) rather than PHPUnit — it is the only WebMCP component that runs in a browser, and its most important behavior is registering and logging nothing when the API is absent, which is the common case. The two load-bearing 8B guards were mutation-tested: removing nonce enforcement fails 2 tests, bypassing the proposal queue fails 2.
- **Declarative forms:** evaluated and rejected for 8B. Codestar renders field titles as `<h4>` rather than `<label>`, emits no `id` on any of its 45 field types' inputs, carries zero `aria-` attributes, and composes bracketed names (`book_options[isbn]`), so a derived schema would have no property descriptions and would bypass `MetaFieldProvider`'s normalized dotted paths. Metaboxes also have no form of their own. The same defects are WCAG 2.1 findings affecting every admin screen today; the fix is vendored-code work tracked separately.
- **Research:** Cloudflare two-phase consumer/producer rollout and Shopify read/steer/no-transact split, including the adoption data that bounds the scope, are recorded in the internal discovery notes.

### 15. Content Relationships (Phase 10A)
- **Purpose:** Let a model declare relationships to other post types in config, and have both sides become readable and writable through REST, MCP, and WP-CLI from that single declaration.
- **Decision:** a relationship is stored exactly once. `RelationshipRegistry` parses the `relationships` config section into `RelationshipDefinition` value objects, then synthesizes the reciprocal on the target model in a second pass so an explicit declaration there always wins over a generated one. The reciprocal shares the same storage key and flips `own_column()`/`related_column()` rather than writing a second row — two rows could disagree, one cannot. The shared key is derived by sorting both endpoint names and pairing both relationship names, so it is identical regardless of model load order and two relationships joining the same models never collide.
- **Custom table, not post meta:** rows live in `{prefix}saltus_relationships`, created lazily by `ensure_table()` in the same style as `ProposalStore` and `AuditLogger`. Every read this feature performs spans two posts; meta storage would need one query per post to answer "what is related to these fifty posts", which is exactly the N+1 pattern `get_related_for_posts()` exists to avoid. The planning docs specified a `src/Migrations/` system with `up()`/`down()` classes — that was deliberately not built, because the repo already had a lazy-creation pattern and a second parallel schema mechanism for one table would be the more expensive choice.
- **Cardinality is enforced from both directions:** `assert_capacity()` checks the near side and then the reciprocal, because a `has_one` declared on one model is only a real constraint if approaching it from the far end is also refused. Re-attaching an existing pair is an update, not a capacity breach.
- **Writes fail closed and whole:** `sync()` validates every target before deleting anything, so a rejected call leaves the existing set intact rather than half-written; it accepts at most 200 ids. Undeclared pivot keys are dropped, keeping the payload from becoming an unbounded unvalidated bucket. A reorder preserves stored pivot values — `upsert()` only rewrites `pivot_data` when the caller actually supplied one. Post ids are filtered on `> 0` rather than truthiness (`PostIdListTrait`), since a negative id is truthy and would otherwise reach a query as a real post reference.
- **Cascade is one-directional:** the synthesized reciprocal is always built with `cascade_delete: false`. Inheriting it would delete the declaring posts when a target is removed, inverting the author's intent. A cascade also spares any target another post still references. Cleanup hooks `before_delete_post`, not `deleted_post`, because resolving which rows to cascade needs the post type, which is gone once the post row is deleted.
- **Governed writes:** `attach_related`, `detach_related`, and `sync_related` are registered in `ProposalService::is_mutating()`, so they queue for human review wherever it is enabled instead of applying directly. That list is a hardcoded allowlist — a new write tool omitted from it would silently bypass the queue, so adding one is part of shipping any mutating tool.
- **Surface:** `Relationships` feature service, `RelationshipRegistry`, `RelationshipDefinition`, `RelationshipStore`, `RelationshipManager`, `PostIdListTrait`, `RelationshipsController` routes (`/relationships/{post_type}`, `/posts/{post_id}/relationships/{relationship}` for GET/POST/PUT, and `.../{related_id}` for DELETE), the MCP tools `list_relationships`, `get_related`, `attach_related`, `detach_related`, `sync_related`, `wp saltus relationship {list|get|attach|detach|sync}`, the `saltus/framework/relationships/{attached,detached,synced}` actions, `ModelRestPolicy::CAPABILITY_RELATIONSHIPS` honoured by both policies, and the guide `docs/guides/relationships.md`.
- **Layout note:** the five tools live in the flat `src/MCP/Tools/` rather than the `Relationships/` subdirectory the planning docs proposed. `WpCliFeatureTest` enumerates that directory to enforce MCP↔CLI parity, and a nested layout would have quietly exempted them from that check.
- **Testing:** six guards were mutation-tested — removing reciprocal-side cardinality enforcement, allowing undeclared pivot keys, validating sync after clearing, dropping relationship writes from the review queue, cascading into a shared target, and letting the reciprocal inherit cascade each fail at least one test. The sync-ordering mutation initially passed, which exposed a test asserting on a row the sync would have kept either way; the test now seeds a row the operation would drop.

### 16. Contributor-Owned Config Validation
- **Purpose:** Stop `ConfigValidator` from reaching into feature internals for their rules, so adding a feature never means editing the validator again.
- **Decision:** `ConfigValidationContributor` is the third contributor contract (beside `RestRouteProvider` and `ToolContributor`), collected the same way by `Core` into a dedicated registry populated **before** the `is_needed()` gate. Config is validated during `init`, before most features decide they are needed, and a section whose contributor was gated out would silently stop being checked — unvalidated looks like a pass. A contributor owns exactly one top-level config section: it supplies both the validation rules (`validate_config_section()`) and the schema fragment (`get_config_schema()`) that feed the generated reference and nearest-match suggestions.
- **Structure:** the `relationships` section is the first contributor. Its rules (`RelationshipConfigRules`) were extracted from `ConfigValidator` and now read cardinalities from `RelationshipDefinition`'s own constants, so rules and enforcement cannot disagree. `Relationships` implements the contract but delegates to `RelationshipConfigRules` — the rules must be constructible with no WordPress at all, because `wp saltus config validate` and CI run them without a boot; dispatch-time checks that need a live site stay where the feature already has its args. Two contributors claiming one section throw `LogicException` at boot: last-wins would silently stop the loser's rules and every config would still pass. A contributor's schema fragment replaces the built-in for its section, and the framework's own rule classes are defaults that a registered contributor overrides rather than doubling (running both would double-report every problem).
- **Shared heuristics:** `SuggestsNearestKey` is a trait, not a base class — contributors are feature services with their own hierarchies — and every consumer agrees on the Levenshtein distance threshold (2), so the same typo gets a suggestion in one section and none in another. A wrong guess is worse than none.
- **Site-level verdicts:** `ConfigValidationSummary` aggregates every model's `ConfigValidationResult` (total/valid/error/warning counts plus flattened problems) and is built by accumulation in `Modeler`, so it reflects exactly the configs that were loaded. A rejected model is recorded before registration bails, because a config that failed to register is exactly what health and the CLI need to report. `Modeler::get_config_validation()` returns `null` until the first config is validated — null means "nothing loaded yet", reported as `config.available: false`, never as a valid site (the absent-source-read-as-clean mistake the v1.8.4 audit corrected).
- **CLI reporting:** `wp saltus config validate` prints a summary and a formatted table of errors, exiting non-zero via the new `CliGateway::halt()`. `_doing_it_wrong` is avoided under WP-CLI because it raises a PHP notice that prints to **stdout** and corrupts `--format=json`; warnings go to the new `warning()` channel (stderr) instead, keeping piped stdout clean.
- **Known top-level keys:** `SchemaBuilder::known_top_level_keys()` lists the seven service ids a model config is read for at depth 0 (`frontend`, `meta`, `settings`, `blocks`, `webmcp`, `ai_context`, `relationships`) plus the keys model classes read directly, each naming the code that reads it. It briefly derived the set from `array_keys( Core::get_service_classes() )`, which accepted every registered feature id — but most features are opt-ins declared under `features:` and `wp_cli` is not a model key at all, so a top-level `admin_cols:` was inert and reported valid. The list is pinned both ways in `SchemaBuilderTest`: the earlier hand-written draft omitted `options`, `settings`, `frontend`, and `blocks`, so every normal config emitted spurious "nothing reads this key" warnings that printed to stdout under WP-CLI and broke `--format=json`.
- **Surface:** `ConfigValidationContributor`, contributor-aware `ConfigValidator`, `RelationshipConfigRules`, `SuggestsNearestKey`, `ConfigValidationSummary`, `Modeler::get_config_validation()`, `wp saltus config validate` (with `--format=table|json|yaml|csv`), the `config` block in the health endpoint (`available`, `valid`, `total`, `valid_count`, `error_count`, `warning_count`), the `docs:config` generator (`bin/generate-config-docs.php`) producing the generated page `docs/api/config-reference.md`, and the `/api/` sidebar section in the VitePress config.
- **Testing:** contributor validation and verdict aggregation are covered by `ConfigValidationContributorTest`, `ConfigValidationSummaryTest`, `SuggestsNearestKeyTest`, `RelationshipConfigRulesTest`, `ConfigCommandTest`, plus expanded `ModelerValidationTest` and `SchemaBuilderTest` and the boot-level `FrameworkBootTest`.

### 17. Relationship Permission Capabilities (Phase 10B)
- **Purpose:** Let a relationship declare separate read and write capability requirements, enforced across every surface — manager, metabox, REST, MCP, and WP-CLI.
- **Decision:** `RelationshipPermissionPolicy` resolves `capabilities.read` and `capabilities.write` lists from a relationship definition and checks each against the current user via a capability checker callback. A relationship with no `capabilities` key is unaffected by the caller's capabilities — deliberately not denied by default, so adding the feature cannot change what an existing site exposes. Read-denied relationships are omitted from `describe()` and return empty from the eager-loading read, making them invisible in the picker and on the post list; a single-relationship read through REST or MCP is refused with `403` instead, because a 200 carrying an empty set cannot be told from a relationship that is genuinely empty. A post type whose every relationship is read-denied registers no metabox at all. Only `read` and `write` are stored — an operation the policy does not define is dropped when the definition is built, so a misspelled key cannot read back as protection that is never consulted. Write-denied relationships render as read-only in the metabox (plain list with no hidden inputs, no data attributes, no remove buttons) and are refused at the manager with `WP_Error` code `rest_relationship_forbidden`.
- **Manager choke-point enforcement:** `RelationshipManager` gates every read and write method through the policy before reaching the store. This is where enforcement happens — the metabox, REST controller, MCP tools, and WP-CLI commands all call the manager, so permission checks run regardless of which surface the request came from. A surface-only check would let a read-denied relationship be queried over REST by the same user who cannot see it in the editor.
- **Reciprocal inheritance:** capabilities are copied to the synthesized reciprocal during registry resolution, because both sides write the same row. A rule declared on `movie.actors` also gates `person.acted_in` — gating one side but not the other would make the rule a bypass.
- **Cascade exemption:** `delete_all_for_post()` bypasses read gates when resolving cascade targets. Cascade is about referential integrity, not user permissions, and routing it through the gated read would let a read-denied user delete a post and silently strand every cascade target. The delete itself is already authorized by whatever allowed the post to be deleted.
- **Addon filter contract:** sibling addons whose namespace is rewritten by Strauss cannot import framework classes, so two WordPress filters pass primitives only. `saltus/framework/relationships/capabilities` adjusts the capability list before resolution, letting an addon impose a rule on a relationship that declares none. `saltus/framework/relationships/can` overrides the final verdict after the capability check, so custom logic (ownership, workflow state) can grant where the capability system denies.
- **Read-only render:** the metabox save path re-checks write permission per relationship before applying changes. A read-only render submits no inputs, so the payload looks like an emptied picker; without this check the save would clear every row on a write-denied relationship — the absent-nonce failure, one relationship at a time.
- **Legacy `capability` key:** the older single-capability `capability` key is still read for back-compat but only gates visibility in the admin UI, never write operations. The guide marks it as legacy and directs authors to `capabilities` with separate `read` and `write` rules for enforcement across all surfaces.
- **Surface:** `RelationshipPermissionPolicy`, gated methods in `RelationshipManager` (`attach`, `detach`, `sync`, `get_related`, `get_related_ids`, `get_related_for_posts`, `describe`, `has_readable_relationships`), read-only render logic in `RelationshipMetabox`, permission checks in `RelationshipsController` (403 on write-denied, and on read-denied through `RelationshipPermissionPolicy::reject_denied_read()`), MCP tools (REST-backed, so `get_related` carries the same 403 and the three writes return `WP_Error` on denial), WP-CLI commands (`wp saltus relationship {attach|detach|sync}` exit with error message on write-denied, `get` returns empty on read-denied), and the filters `saltus/framework/relationships/capabilities` and `saltus/framework/relationships/can`.
- **Testing:** `RelationshipPermissionPolicyTest` covers resolution (no rule leaves access unchanged, bare string accepted as single capability, malformed rules treated as no rule, reciprocal inheritance, filter contract). `RelationshipPermissionSurfaceTest` proves enforcement actually runs at the manager (attach/detach/sync refused when write denied, refused sync leaves stored rows intact, write through reciprocal also refused, reads return empty when read denied, describe omits read-denied relationships, the metabox does not register when every relationship is read-denied, write denial does not hide reads, cascade resolves targets even when read denied, metabox renders read-only when write denied, read-only render does not clear on save).

### 18. Audit Rollups & Observability (Phase 14)
- **Purpose:** Let an operator see per-ability and per-client call volume, error rate, and latency over a chosen window without scanning the audit table, and keep those aggregates once retention has pruned the rows they came from.
- **Decision:** `RollupStore` pre-aggregates one row per day and ability into `{prefix}saltus_mcp_audit_rollups` (`DailyRollup` is the value object: counts, error/exception/validation/rate-limited tallies, avg plus p50/p95/p99/max duration, and the sampling rate in force). Rollups are computed on the existing retention cron — `AuditLogger::cleanup_expired_entries()` calls `compute_recent_rollups()` *before* the delete, so aggregates outlive their source rows. It rolls up yesterday and the day before, because a late-arriving entry would otherwise be lost to the pass that already covered its date, and it hands `RollupStore` its own `AuditDatabase` adapter rather than letting the store resolve the global — the read and the prune must run against the same database. Computation is gated by `saltus/framework/mcp/audit/rollup_enabled` (default `true`).
- **Empty string, not NULL, for aggregate rows:** the unique key that keeps one row per day, ability, and client cannot constrain NULLs — a unique index permits unlimited ones — so aggregate rows, which is what the default mode writes, would have no uniqueness at all and every repeated or overlapping rollup of a date would stack another duplicate that reads back as extra traffic. `AGGREGATE_CLIENT` is the empty-string sentinel those rows carry instead.
- **One atomic upsert:** `store_rollup()` writes a single `INSERT ... ON DUPLICATE KEY UPDATE` against the three-column unique key rather than a read-then-write, so two concurrent rollups of the same date cannot both see "no row" and both insert. The statement is built from the `ROLLUP_COLUMNS` map — placeholder order comes from the map, not from the value array, so reordering either one cannot silently misalign the arguments — and the key columns are left out of the update list.
- **Client rows are a separate series, not a mode:** `get_rollups()` returns aggregate rows only, and `get_client_rollups()` is the separate read for the client dimension, so a site that enables the per-client dimension (`saltus/framework/mcp/audit/rollup_by_client`, default `false`) cannot double-count its own totals. Client rows are keyed by the persisted opaque `ClientIdentity` value; no raw visitor address is stored or surfaced.
- **Schema version 1.2.0 with a migration:** `RollupStore` is the fourth store on the lazy `ensure_table()` pattern (after `AuditLogger`, `ProposalStore`, and `RelationshipStore`) and the first one with an actual schema *change* to make, which is the condition Phase 10A set for a migration earning its place. A fresh install needs none of it — the `CREATE TABLE IF NOT EXISTS` already carries the current schema — so the upgrade path runs only when `saltus_mcp_audit_rollups_db_version` holds an earlier value: 1.0.0 gains the `client_identifier` and `sample_rate` columns; 1.1.0 → 1.2.0 normalizes NULL identifiers onto the sentinel, collapses the duplicates already stored, makes the column `NOT NULL`, and replaces the two-column unique key with `(rollup_date, ability, client_identifier)`. The duplicate collapse is a self-join `DELETE`, not a subquery, because MySQL cannot read the table a `DELETE` targets in a subquery. The statements carrying the 1.2.0 correctness fix are plain SQL so they apply on MySQL and MariaDB alike; the `IF NOT EXISTS`/`IF EXISTS` guards on the older column and index statements are MariaDB syntax, and making those portable is tracked separately.
- **Freshness is recorded, not inferred:** `record_completion()` stores `saltus_mcp_rollup_last_completed_at` after a cycle finishes. Inferring freshness from the newest rollup row would report a stalled cron for any site that simply had no traffic — a no-traffic day produces no rows and is still a valid, complete rollup. `get_freshness()` reports `disabled`, `unknown`, `fresh`, or `stale`; `HealthController` returns it under `rollups` and reports `degraded` when rollups are enabled, stale, and the audit sample is non-empty, so a stalled cron is visible rather than silent.
- **Slow calls are logged outside sampling:** a call over `saltus/framework/mcp/audit/slow_threshold_ms` (default 5000) is written to `{prefix}saltus_mcp_audit_slow_calls` *before* the sampling decision, so the calls most worth seeing are not the ones sampling discards, and pruned on its own `saltus/framework/mcp/audit/slow_retention_days` (default 90) — a slow-call record is worth keeping longer than a routine one.
- **Sampling precision:** `SAMPLE_PRECISION` (1,000,000) bounds the `wp_rand()` draw *and* divides it, so the retained fraction is `floor(rate * N) / N` — exact for any rate expressible in millionths. The draw and its divisor sharing one constant is the point: when they disagreed, every rate below 1.0 discarded very nearly everything while the rate persisted with each rollup still claimed the configured proportion had been kept.
- **Surface:** `src/Features/Observability/` holds `ObservabilityDashboard` (a `manage_options` management page at Tools → Saltus Metrics, gated by `saltus/framework/observability/dashboard_enabled`, enqueuing `assets/Feature/Observability/dashboard.js`/`.css` only on its own screen hook alongside core Chart.js and `wp-components`) and `MetricsApi` (the `wp_ajax_saltus_get_metrics` reader: nonce first, then `manage_options`, then the windowed read clamped to 1–365 days). The capability check branches into an `else` rather than returning after `wp_send_json_error()` — the stubs declare that `never`, so relying on it to stop the work means any context where the send does return falls through into the query with the check already failed. `MetricsCommand` registers the `saltus metrics` group (`summary`, `per-tool`, `per-client`, `health`, with `--since`, `--ability`, and `--format`), writing through `CliGateway` rather than static `WP_CLI` calls like every other command group.
- **Testing:** `RollupStoreTest` (arithmetic, percentiles, the upsert, and the absent-database case), `DailyRollupTest`, `RollupRetentionTest` (rollups computed before the retention delete, both target dates, rollups still run when retention is disabled and retention still runs when rollups are, and the write goes through the `AuditDatabase` seam), `MetricsApiTest`, `ObservabilityDashboardTest`, `MetricsCommandTest`, plus `HealthControllerTest` for the freshness payload and `AuditLoggerTest` for sampling and slow-call recording. `RollupTestDatabase` is the shared `AuditDatabase` double these use.

## Naming & Standards
- **Quality Assurance:** PHP CodeSniffer (PHPCS) ensures adherence to WordPress coding standards, while PHPStan handles static analysis to catch type errors and logical bugs early.
- **Testing:** Automated tests are powered by PHPUnit, ensuring framework stability across different WordPress and PHP versions.
